# Architecture decisions (cross-plan reconciliations)

The mobile, backend and recommendation plans were written in parallel. Where they proposed different answers to the same question, this page records the single choice that all three docs now follow, and why.

Related docs: [`backend.md`](backend.md), [`mobile.md`](mobile.md), [`recommendations.md`](recommendations.md), [`schema-changes.md`](schema-changes.md). Each decision is also logged in [`plan.md`](plan.md).

| # | Topic | Options seen | Decision | Why |
|---|---|---|---|---|
| 1 | Behaviour events table | `analytics_events` (mobile) · `user_events` (backend, recommendations) | **`user_events`**, partitioned monthly, plus `identity_links` | One table feeds analytics and recommendations; the richer recommendations schema (surface, position, strategy, request ID) covers the mobile fields too |
| 2 | Push tokens table | `device_push_tokens` (mobile) · `push_tokens` (backend) | **`push_tokens`** with the merged columns: `user_id, app, platform, token unique, provider, app_version, locale, last_seen_at, revoked_at` | Shorter name; nothing lost |
| 3 | Consent records | `user_consents` (mobile, backend) · `consents` (recommendations, also covers anonymous visitors) | **`consents`**, keyed by user ID **or** anonymous ID, append-only, purposes `analytics`, `personalisation`, `marketing_sms`, `marketing_email`, `marketing_push`, `location_tracking`, `terms`, `privacy` | Anonymous visitors must be able to give and withdraw consent before signing in |
| 4 | Realtime transport | WebSocket (mobile) · SSE (backend) | **Server-Sent Events** everywhere; mobile uses `react-native-sse`, falling back to polling | Data only flows server → client; SSE needs no extra gateway and works through nginx; riders send location with plain POSTs |
| 5 | "Moniepoint" online payments | `moniepoint` provider value | Online card and transfer payments go through **Monnify** (Moniepoint's gateway). The provider value stays `moniepoint`, documented as "Monnify online". Moniepoint POS terminals in stores are a separate integration | Matches how the business is integrated in practice |
| 6 | API wire format | Client used `uk-used`, `techshop/vendor`; schema uses `uk_used`, `first_party` | **camelCase JSON fields, snake_case enum values** (match the database). URL slugs like `uk-used` stay a UI concern | One contract generated from the OpenAPI spec; no translation layer in the API |
| 7 | Product shape in the API | One flattened listing (client) vs multiple listings per variant (schema) | `ProductSummary` for cards (best offer) and `ProductDetail` with `offers[]` (all listings) | Marketplace needs "other sellers" |
| 8 | Delivery OTP storage | `verification_codes` (purpose `delivery_otp`) · `delivery_jobs.otp_hash` | **Only on `delivery_jobs`** (`otp_hash`, `otp_expires_at`, `otp_attempts`, `otp_verified_at`, `proof_method`) | One place to check; fixes the "delivered without verifying the OTP" gap |
| 9 | Sample data location | `frontend/packages/fixtures` (web only) | Move to **`shared/fixtures`** with `createFixtureClient()` matching the real client | Mobile can't import web packages (separate install roots); both build screens before the API exists |
| 10 | Migration order | `database.md` §9 phases | **Revised order in [`backend.md`](backend.md) §4.1**: platform tables first; content and tracking in M1; marketing in M2 | Outbox, audit and idempotency are needed from day one; deals and CMS pages are on the first screens; tracking must start at launch |
| 11 | Recommendation integration | Batch-only, replica, live service | **Combined:** Go rules fallback + nightly Python batch via internal API + Go session re-rank + gated live Python service. **Replica rejected** | Keeps "only Go touches the database"; see [`recommendations.md`](recommendations.md) §4 |
| 12 | Redis | — | **Not at launch.** River (jobs), database counters (global limits), Postgres `LISTEN/NOTIFY` (realtime) | One fewer stateful service; added later behind interfaces |
| 13 | Web auth tokens | Browser-held tokens vs server-held | **Backend-for-frontend:** Next.js apps keep tokens in their own `httpOnly` cookies; the API is cookie-free and takes `Authorization: Bearer` | No CSRF surface on the API; same API for web and mobile |
| 14 | Payments in the mobile app | WebView vs provider SDKs vs auth session | **`expo-web-browser` auth session** + server-side verification + status polling | Keeps 3-D Secure, bank-app and USSD hand-offs working; no card data in the app |
| 15 | Guest checkout | Web allows guests; app proposal requires sign-in | Web: guest checkout with phone OTP at checkout. App: sign-in at checkout (light phone OTP). **Owner to confirm** | Accounts are needed for push and tracking; phone OTP keeps it light |
| 16 | Message log | New `messages` table vs extend `notifications` | **Extend `notifications`** into the per-recipient message log and in-app inbox, plus `message_events` ([`messaging-marketing.md`](messaging-marketing.md) §6) | One place for every message; the in-app inbox already reads it |
| 17 | Counters for limits and risk | Redis · per-module tables | **Postgres window counters** (`auth_rate_limits`, `velocity_counters`) with the same design, shared by identity and the risk engine | Consistent with #12 (no Redis); works across API instances |
| 18 | OTP delivery | Identity calls the SMS provider directly vs through messaging | **Through `notify.Send` on the `critical` queue**, with its own workers and backup SMS provider | Marketing load can never delay sign-in codes; one provider integration |
| 19 | Sensitive actions | Per-module approval rules | **One pattern everywhere:** a sensitive permission (★) needs MFA within 10 minutes (step-up), and the approver must differ from the requester (refunds, payouts, adjustments, campaigns, KYC, MFA resets) | Same controls and audit trail in finance, marketing, trust and admin |
| 20 | Fraud scoring | Python model service vs Go rules | **Rules in Go at the checkpoint** (30 ms budget, versioned, test bench); a learned model is added later as one more signal | Must run inside requests and fail safely; labels don't exist yet at launch |
| 21 | Search engine | Postgres vs Meilisearch/OpenSearch at launch | **Postgres read model** (`product_offer_summary`, FTS + trigram) behind `search.Port`; switch only at measured thresholds | One fewer system to run; swap-ready |
| 22 | Account-takeover payout protection | — | **24-hour payout hold** after any phone, email, password or bank-account change, enforced by payouts, defined in identity, scored in trust | Closes the most common seller-takeover theft path |
| 23 | Who funds a discount (2026-10-05) | Store funding per order line (schema change) vs derive it | **Derive it:** seller-funded promotions target only that seller's listings and never carry coupons; a line's discount has a single funder; TechShop-funded marketplace discounts post to `expense:promotions` | No schema change while the database is frozen; the ledger can still pay sellers correctly |
| 24 | Order subtotal and VAT (2026-10-05) | Gross subtotal vs net subtotal | **`subtotal_kobo` is net of VAT** so the schema's total check holds with VAT-inclusive consumer prices; the API returns the gross `itemsKobo` for display. VAT rate and scope are placeholders | Keeps the database check; finance confirms the VAT treatment |
| 25 | Live payment adapters (2026-10-05) | All three providers live vs fakes first | **Fakes for all three; a live adapter for Paystack only.** Config refuses enabling Monnify or OPay outside development until their adapters are built and confirmed against the sandboxes | No live keys or calls during the build; a provider can't be switched on half-built |
| 26 | Audience rules (2026-10-05) | Free-form SQL vs a rules language | **Typed allowlist compiled to parameterised SQL** (`marketing.Rules`) — the second sanctioned dynamic query after search | Marketing can combine filters freely without any injection surface |
| 27 | Rider or carrier (2026-10-05) | Decide at checkout vs at packing | **At packing:** an address inside a delivery zone gets an own-rider job; anywhere else a carrier shipment. Carriers are a port with only a fake adapter until the owner picks couriers | The zone list can change between checkout and packing; no live courier calls during the build |
| 28 | Rider device binding (2026-10-05) | Device id from a request header vs from the session | **From the signed-in session** (recorded at OTP sign-in), checked against phones approved by someone other than the rider | A header can be forged; the session can't |
| 29 | Recommender data | Python reads Go's DB · Go reads Python's DB · each owns its own | **Each service owns its database.** Python gets a private Postgres (`recs-postgres`); a Go job pulls results through the recommender's authenticated API into `personalisation.rec_*`; the site serves from Go with rule fallbacks. Pseudonymised data only. Supersedes "Python has no database" in recommendations.md §4 (owner, 2026-10-06) | Independent schemas and scaling; the shop never depends on Python being up; no cross-service DB coupling. Postgres over MongoDB: model outputs are tabular, one database technology to run |
| 30 | Redis | Not at launch (#12) | **Supersedes #12 (owner, 2026-10-06): Redis is allowed.** Use it for caching and speed: rate-limit and velocity counters (#17), a shared permission cache, cross-instance live updates, page, search and autocomplete caches, guest carts, provider breakers, and short-lived codes and locks. **Postgres stays the source of truth** for money, orders, stock, sessions and refresh tokens, audit logs and River jobs. Flash-deal and coupon limits keep their Postgres check as the final guard | Faster hot paths and multi-instance scaling. Redis needs a password and ACLs, TLS in production, no public exposure, and keys namespaced (`.claude/rules/01` §7) |
